# PBZ PvP 网络预留设计

状态：设计与接口草案；没有实现联机、伤害 Hook 或服务器。2026-11-08。

## 两种模式

1. DirectHost：客户端直连房主，房主运行游戏和对局判定。这里的 P2P 指房主星形拓扑，不要求所有玩家两两互连。
2. Relay：所有玩家（包括房主）连接中继，仍由房主运行游戏和判定。中继只管理连接、房间及消息转发，不启动游戏。

RoomSession → CombatAuthority / GameAdapter → IRoomTransport；DirectHostTransport 与 RelayTransport 实现相同传输接口。传输模式与判定权分开，协议不能把“来自中继”当成“可信的伤害结果”。

## 中继改善的边界

中继可减少房主向多个玩家重复发送相同快照的上行负担（协议应支持一次广播请求），也可能改善玩家间的路由。它不能消除房主上行丢包、网络中断或游戏线程停顿。房主的输入和判定仍需经过房主网络。其他玩家可以继续收到彼此的表现快照，但不能在没有权威结果时独立确认伤害和胜负。

不得使用“等待每名玩家本帧输入齐全才推进”的全局锁步。慢客户端只影响自身输入；快照不排队补发，可靠事件与快照分开处理，每个连接限制发送队列，过期快照直接丢弃。房主卡顿采用短时表现外推和明确超时；首版房主失联结束对局。房主迁移需要另行实现一致快照、选主与 authority epoch，不能声称中继天然支持。

若要求房主卡顿仍能继续权威战斗，需要独立对局判定服务或更复杂的判定权迁移。独立服务可以不渲染，但必须拥有足够的碰撞、动作和伤害规则；纯消息转发无法替代这些规则。

## 对局和伤害

房主选择竞技场及统一角色预设；保留个人原存档，对局不得直接覆写。玩家进入后同步规则版本、Mod 版本、角色预设摘要及地图标识，全部加载确认后开始。协议不允许客户端请求任意资产路径或任意函数执行。

实体使用独立 EntityId，不能传 UObject 指针或仅凭本机对象名称匹配。输入和攻击意图带玩家、序号、对局 epoch 和 tick。客户端即时播放本地表现，房主验证攻击阶段、距离、目标、无敌/防御状态，发布带事件 ID 的 CombatResult；去重后更新血量、死亡和 HUD。玩家无法直接提交最终伤害或最终血量。远端角色仅播放表现，不能再次计算并应用同一笔伤害。

左上角血条使用独立玩家列表和权威 HealthState：PeerId、显示名、当前/最大生命、死亡、连接状态及递增状态版本。晚加入必须取得完整快照。首版可限制比赛开始后只允许观战或禁止加入。

## 协议与中继

NetworkContracts.h 是接口草案，不是可直接 memcpy 的线协议。序列化需明确枚举值、字节序、长度上限、版本协商、房间成员认证及消息大小限制。房主可发送战斗结果，普通成员只能发送允许的输入/意图消息；服务器绑定连接身份，拒绝伪造 sender、跨房间路由、重放旧 epoch。

高频位移/朝向/动作快照使用不可靠有序通道（丢旧留新），准备、地图加载、伤害、死亡和结算使用可靠有序事件通道。可靠传输与拥塞控制由选定后端实现；不能以裸 UDP 直接宣称已完成。

## 验证顺序

1. 离线生成第二角色，确认不是共享输入、相机或玩家单例；竞技场及存档隔离。
2. 确认双向攻击碰撞、阵营过滤、伤害、受击、格挡/弹反、死亡及复活。
3. 两实例局域网：位移、动作、伤害与全员血条一致。
4. 同一协议切换 DirectHost/Relay，确认相同行为。
5. 对慢客户端、房主丢包/卡顿、中继断线、重复事件与晚加入分别测试。

任何“原生 PvP 可用”的结论必须先通过第 1、2 项；引擎自带网络代码或函数名不能替代验证。
